# Region 9 Live Studio 17.1 production pipeline

## Root cause

RC1 had three contracts that did not meet. Validation wrote normalized decisions to `r9ls_current_products`, while Forecast Production primarily rendered `r9ls_published_products`. A late RC1 code path attempted workspace generation, but the scheduler constructed a short-lived generator independently of the plugin's authoritative generator, workspace persistence remained an incidental side effect, and the admin renderer silently substituted published products whenever the workspace shape did not match `['products' => ...]`. On a first run the material-change detector intentionally skipped products with no prior comparison, so no approval-queue records existed; the material-change approval methods were nevertheless wired to the apparent Forecast Production actions. Consequently the checked-in RC1 architecture had no complete product-level lifecycle even where the partial generator populated rows. Decision History was also the material-change decision array rather than a record of successful validation runs.

The staging combination “successful validation plus no workspace option” cannot be produced by the late partial scheduler method in this repository without a runtime/deployment mismatch or a suppressed generation failure: that method calls workspace refresh before recording success. The repair therefore removes that ambiguity rather than claiming the unavailable staging artifact matched this exact checkout. It injects one authoritative generator, returns the persisted workspace in the validation result, and tests first-run/manual/scheduled persistence directly.

17.1 makes generation a required part of every successful scheduler run. The scheduler uses the authoritative generator instance, passes the normalized decision and grouped changes, and does not complete the validation response until the workspace and Decision History are stored.

## Validation-to-publication lifecycle

1. Manual and scheduled validation collect and normalize source state.
2. The rule engine creates the current decision output and the material-change engine records field-level changes.
3. The product generator sanitizes enabled product IDs. Empty, non-array, or wholly invalid configuration falls back to all canonical definitions.
4. Exactly one private workspace row is generated for each enabled canonical product. Field changes are grouped inside their responsible product row.
5. Stable content is hashed. A matching prior workspace or public hash retains its product version and becomes `unchanged_available_for_review`; changed content increments the prior version and becomes `changed_pending_review`.
6. The workspace envelope and generation metadata are persisted before validation returns. A bounded Decision History record is appended for the successful run.
7. An authorized editor approves or rejects individual or selected products. Approval never implies publication. Automatic publication remains off by default and newly generated rows remain pending review.
8. An approved product can be explicitly published. Only that product is promoted to canonical state and only its public cache (plus the aggregate public cache) is invalidated.
9. Publishing appends immutable publication history and updates latest-publication metadata. Public REST and theme helpers read only canonical approved/published records.

## Workspace schema

The workspace envelope contains `schema_version`, `workspace_reference`, `generated_at`, `generation_duration`, `actor`, `approval_reference`, `source_version_reference`, `prior_publication_reference`, `changed_products`, and a `products` map.

Each product row contains the canonical product ID/title, current and previous version, stable content hash, workspace/approval/publication states, score, risk label/class, confidence, counties, normalized timing, summary, discussion, optional media ID/URL, grouped changes/count, generated timestamp/duration, actor, approval reference, workspace/source/publication references, and compatibility product fields. Drafts are always private until explicit publication.

The hash includes stable product identity and forecast content. It excludes generated/published timestamps, request duration, approval data, workspace references, and other transient state, preventing version churn from operational metadata alone.

## Decision History schema

Each `validation_decision` record contains a unique decision ID, validation mode/time/actor, sanitized source-health summary, Region 9 risk, confidence, counties, timing, material-change count, product-grouped changes, generated product IDs, generation and validation durations, prior publication reference, and resulting workspace reference. Records are prepended and bounded to 300 entries; existing records are preserved by migration.

## Approval rules

- Capability and nonce checks are mandatory for all admin actions.
- Product IDs are sanitized and validated against canonical definitions.
- Only an existing workspace row can be approved or rejected.
- Rejection requires a reason and records actor, timestamp, reference, and blocked publication state.
- Approval records actor, timestamp, and an approval reference but does not publish.
- Batch approve selected/all, reject selected, and publish approved actions invoke the same isolated product methods as individual actions.

## Publication and rollback rules

Publication requires an approved, non-rejected workspace row. Missing/malformed IDs, unapproved or rejected rows, and duplicate version/hash pairs fail closed and generate audit events. The previous public option is not changed by blocked actions. A successful promotion records a full immutable snapshot, latest metadata, and targeted cache invalidation.

Rollback requires a matching historical product/reference snapshot. It restores only that product, leaves all history intact, creates a new `rollback` publication event, updates latest-publication metadata, and invalidates only that product and the aggregate cache.

## 17.1 migration

`R9LS_Product_Generator::migrate_17_1()` runs on plugin boot and activation. It converts recognized flat RC1 workspace rows into the 17.1 envelope, repairs missing/non-array workspace and history containers, and records `r9ls_17_1_migration`. It never deletes or rewrites published products, product history, material changes, overrides, or canonical alert state. The completion marker makes subsequent runs no-ops.

## Public/private boundary

`r9ls_forecast_production_workspace`, normalized decisions, decisions, and publication snapshots are private. REST and theme functions only return records from `r9ls_published_products` where both `approval_state=approved` and `publication_state=published`. Rejected and pending drafts cannot reach public routes, shortcodes, widgets, or homepage helpers. Until explicit publication, existing homepage unavailable fallbacks remain in effect.

## Audit events

Structured contexts identify `validation_completed`, `workspace_generated`, `product_unchanged`, `product_changed`, `product_approved`, `product_rejected`, `product_published`, `publication_blocked`, `publication_failed`, `rollback_completed`, `rollback_failed`, and `migration_completed`. Operational errors retain warning/error levels; informational history does not replace current scheduler/source health.

## Troubleshooting

1. Confirm `r9ls_last_validation.status` is represented by a healthy scheduler record and inspect the latest audit event.
2. Confirm `r9ls_forecast_production_workspace.products` is a map keyed by enabled canonical product IDs.
3. If the workspace is absent, run manual validation and inspect `r9ls_product_generation_last.workspace_rows` and `workspace_reference`.
4. If duration is unavailable, verify generation metadata exists; a valid zero duration displays as `0.000s`.
5. If publication is blocked, inspect that row's approval/publication states and the structured `publication_blocked` audit reason.
6. If public pages remain unavailable after publication, confirm the canonical product is both approved and published and clear only the affected `r9ls_public_product_<id>` and aggregate cache if necessary.
7. Run `php scripts/validate-v17.1-production-pipeline.php` to exercise the 30 required lifecycle assertions without external weather requests.
